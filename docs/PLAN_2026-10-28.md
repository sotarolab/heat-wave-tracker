# Plan: from heat wave tracker to a verified forecasting service

Written 2026-10-28. This repository becomes a public, year-round, station-level forecasting
service for daily highs and lows, with every forecast stored before settlement and scored every
night against the raw models, the NWS and an AI model. The heat wave map becomes one view on it.
The repository stays; the name follows once the scorecard has rows.

Two products come out of it. The scorecard, which nobody publishes for free at station level.
And the process: a repository whose history shows an AI building a scored model under tests,
gates and review, which is the answer to "AI code is vibe-coded".

## Decisions already made

| Question | Decision | Why |
|---|---|---|
| New repo or this one | This one, restructured in place on a branch | Keeps the archive logging since 2026-07-15 across 164 stations, the Render deploy, CI, Docker, nine test files and 343 commits of visible history. |
| Frontend | React + TypeScript + uPlot, ported from an existing private client; Dash retired at parity | The interface is good; the latency was Python computing on the request path, not the client. |
| First target | US daily high and low at ASOS stations, verified against the NWS CLI | Official verification number exists; the archive is ready. |
| Second target | Chile: DMC stations, highs and lows on the same spine (week 4), then daily rain | The scalability test of the entity key; real need, no competition. Rain after 60 days of raw-model scores. |
| Model | LightGBM quantile, pooled across stations, conformal bands, kriged-residual stage kept | NaN-native, monotone constraints, measured spatial gain (1.612 → 1.469 °C RMSE). |
| Private side | Only public feeds enter this repository; no third-party or proprietary data | Private downstream applications import this package and add their own inputs on top. |

## What is wrong with the current ML

| Observed | Why it matters |
|---|---|
| Target is hourly 2 m temperature | Nobody decides on it. Daily high and low are what people act on and the only target with an official number. |
| Leads ≤ 8 h | A limit of the logging schedule, not the science. |
| GFS only, deterministic | The scorecard cannot say "beats HRRR, NBM, ECMWF and the NWS". |
| Quantile bands cover 79.7% at a claimed 95% | Conformal calibration was meant to gate deployment and never happened. |
| No stored predictions | Shadow logging was the next follow-up and was not built. |
| Correction applied at render time in `app.py` | Cannot be reused by a backtest, an MCP server or a bot. |

## Architecture

```
heat-wave-tracker/
  pyproject.toml           one install; extras [service] [ml] [dev]
  CLAUDE.md                one page: the rules below and the commands
  src/heat/
    config.py              settings from env, validated once (pydantic-settings)
    ingest/                one module per feed; typed frames; never raises; writes heartbeat
    store/                 Postgres via SQLAlchemy Core; Alembic; read(entity, as_of) only
    features/              pure functions (frame in, frame out); versioned names
    forecast/              Forecaster protocol + implementations; artifact registry
    evaluate/              scoring, golden backtest, scorecard builder
    serve/                 FastAPI routes, MCP server, assistant; read-only
  client/                  React, TypeScript, uPlot, Leaflet; types generated from OpenAPI
  scripts/                 thin entry points: ingest, score, train, build
  tests/unit  tests/properties  tests/golden
  docs/ARCHITECTURE.md  docs/decisions/  docs/ml/EXPERIMENTS.md
  alembic/  Dockerfile  render.yaml  .github/workflows/
```

Dependencies point down only: serve → evaluate, store; forecast → features, store; features →
pandas only. `import-linter` enforces it in CI.

The new package starts empty. Candidates for porting, one module at a time and only after it
has been read and its purpose stated in one sentence in `docs/PORT_LOG.md`: `bias.py`,
`correction.py`, `extremes.py`, `assistant.py`, `asos.py`, and `da/gefs_members.py` for the
spread feature. The rest of `da/` is not ported. The nine existing test files are the
acceptance bar: a ported module still passes them. `app.py` and the scripts are never
ported; they are rewritten against the new tables.

### Rules

- **Point in time, always.** Every stored row has `valid_at` and `received_at`, UTC, tz-aware.
  Every read takes `as_of` and returns only rows with `received_at <= as_of`. Local day is
  derived in one tested module and nowhere else.
- **One path.** The function that forecasts today at 10:00 is the function that backtests
  15 July at 10:00.
- **Nothing computes at request time.** Scheduled jobs write tables; routes read tables. A route
  that does more than a query is wrong.
- **The client computes nothing.** Edge, consensus, model pick, unit conversion live in Python
  with tests. A component holding arithmetic beyond pixel math is a bug.
- **Frames have schemas.** pandera at every function boundary that passes a DataFrame.
- **Feeds never raise.** Empty typed frame on failure, heartbeat row written, `/healthz`
  reports each feed's last success.
- **A feature ships only if it has a line on the scorecard.** If you would not notice when it
  stopped working, it does not belong.

### Database

Postgres on Neon, Alembic. Append-only except `stations` (edited by hand) and `scores`
(derived; rebuilt in place from predictions and settlements). A corrected observation or
a reissued CLI is a new row with a later `received_at`; reads take the latest row with
`received_at <= as_of`.

```
stations      station_id, network, name, lat, lon, elev, tz, settles, settlement_source,
              tier, active
observations  station_id, valid_at, received_at, source, var, value, precision
              PK (station_id, valid_at, source, var, received_at)
model_runs    model, station_id, run_at, received_at, source, var, step_h, values float4[]
              PK (model, station_id, run_at, var)
              one row per run and variable; the hourly horizon is the array
settlements   station_id, local_day, target, value, source, received_at
              PK (station_id, local_day, target, received_at)
predictions   forecaster, version, station_id, target, local_day, as_of, received_at,
              quantiles jsonb, features jsonb
              PK (forecaster, version, station_id, target, local_day, as_of)
scores        forecaster, version, station_id, target, local_day, lead_h,
              mae, crps, brier, covered_90, computed_at
              PK (forecaster, version, station_id, target, local_day, lead_h)
heartbeat     feed, last_success, last_error, rows
```

Indexes: (station_id, valid_at) on observations; (station_id, run_at, model) on model_runs;
(station_id, target, local_day) on predictions and scores.

Scale: the 165 ASOS stations already in the archive, six models, four slots a day, three
variables per model (temperature, dewpoint, cloud cover). That is about 12,000 model_runs
rows a day and under 3 GB a year. Variables are added only when a feature on the scorecard
needs them. model_runs rows older than 18 months roll off to parquet; they are inputs, and
the history of what was known lives in predictions, which never rolls off.

### Issue slots and lead

Predictions are issued at fixed local slots, 00:00, 06:00, 12:00 and 18:00, one row per
station, target and slot. Each target is scored at the six slots before its typical time:
for the high, day-ahead 06:00 through same-day 12:00; for the low, 18:00 two days before
through 00:00 on the day. The same-day slots carry the running observed maximum or minimum
as a feature. Baselines are sampled at the same slots through the point-in-time read, so
every column on the scorecard saw the same information.

Beyond the six-hourly ladder, one slot a day carries the longer leads: the 18:00 local slot
issues for days 2 through 5. That is the "evening before" cadence anyone planning outdoor
work or activities uses, and it adds four rows per station and target per day. The raw
globals and NBM reach day 5; HRRR does not, and its column is empty there.

`lead_h` is the hours from the slot to the end of the target's local day. It is unambiguous
for both targets and in a backtest; the scorecard displays by slot name and day-ahead number.

Ingest stores the latest run per model available at each slot, not every run. HRRR goes from
24 runs a day to 4. Training takes one sample per station, day and slot, with lead as a
feature in one pooled model.

### Entity key and the spatial extension

The station is the entity, and `station_id` is namespaced by network (`asos:KDCA`,
`dmc:330020`). `stations` carries `network`, a `settles` flag (whether the station has an
official daily number) and a `tier` for observation quality. Any station with a location can
be an observation source without being a forecast target.

Spatial features live in `features/` as functions of a target station and a frame of nearby
observations with lat, lon and elev. They never know which network the neighbours come
from. The kriged-residual stage reads observations by location, not by network. A private
downstream package can register a denser station network in its own database and get richer
neighbour features from the same code, with nothing added here.

### Frontend

```
client/src/
  api/         types.ts generated from the OpenAPI schema; one fetch per route
  components/  StationChart, Scorecard, StationMap, ModelTable
  pages/       Scorecard (home), Station, Model, About
  theme.css    the existing 197-line stylesheet, unchanged
```

One route per pane, one query per route. Time series travel as columnar arrays. Stale-while-
revalidate so a cold start never shows a blank pane. The Scorecard page is the first page
built, in step 4, since it is new and needs no parity. The Dash app runs until the React
station page reaches parity in step 6, then goes.

## The model

- LightGBM quantile loss, pooled across all stations with station as a feature; monotone in the
  running maximum once same-day observations exist; trained on every issue slot out to day 3.
  Days 4 and 5 are scored raw first and join the model once the scorecard shows there is
  skill to add there.
- Conformal calibration on the most recent held-out weeks; a 90% band must cover 90% there
  before a model is deployed. Calibration on one block drifts with the season, so the
  scorecard's `covered_90` is the live monitor: per lead bucket over a trailing 30 days it
  must stay between 85 and 95, and a breach fails the nightly scoring job.
- Weekly retraining behind a champion–challenger gate on the golden backtest. Artifacts versioned
  by git SHA and training window, stored with feature names.
- Kriged-residual second stage kept.
- Baselines on the same scorecard: global GFS, ECMWF IFS (open data) and ICON; CONUS HRRR
  and NBM; the NWS forecast; persistence; climatology from CLI normals. The three globals are
  the whole raw set for Chile. NAM is skipped (on NCEP's retirement path); AIFS is skipped
  by choice.
- Spread enters as features, not as a flag: inter-model spread of the daily extreme across
  the raw models, and GEFS member spread. The band width is the uncertainty signal, and the
  scorecard reports error and coverage by spread tercile so a useless signal is visible.

## Engineering practice

- **Gates arrive with the code they protect.** import-linter in the first commit; the golden
  backtest the day the scorer exists; hooks when the first PR opens. Tooling that precedes the
  thing it guards is also vibe engineering.
- **Three test layers.** Unit on pure functions. Property tests (hypothesis): later `received_at`
  changes no output; distributions sum to one; the floor never exceeds the settled high; DST
  round-trips. Golden backtest: a committed scorecard; CI fails if a number moves without the
  file changing in the same commit.
- **Numbers exist only as CI output.** A metric stated in a conversation is not a result until it
  is a row in `docs/ml/EXPERIMENTS.md` with its commit.
- **ADRs** in `docs/decisions/`, one page, dated, written in the session the decision is made.
- **Division of labour by verifiability.** AI writes adapters, migrations, routes, the client,
  and the tests for those. The science tests in `features/` and `forecast/` are written by a
  person first, as the claim the code must then meet. `features/` and `forecast/` stay small
  enough to be read line by line.
- **Small PRs, plan mode for multi-layer changes, code review skill before human review.**
- **Repo skills** (`.claude/skills/`): backtest, migration, experiment, adr, feed.
- **README carries a "how this was built" section**: what the agent wrote, what was reviewed by
  hand, what gates every change passed.

## Order of work

1. **Skeleton (first commit).** pyproject with src layout, CLAUDE.md, import-linter contract,
   the architecture ADR, CI running ruff, mypy and the existing tests.
2. **Store and ingest (≈2 weeks).** Day one is a feed spike: one station, one slot, daily
   high and low from all six sources, and a committed table in `docs/ARCHITECTURE.md` of
   source, variables, horizon and update cadence per model. Then the six tables; Open-Meteo
   previous-runs backfill to mid-July; CLI ingest; the lookahead property test.
   Backfilled rows are marked `source = backfill`, and their `received_at` is the run time
   plus a per-model latency constant documented next to the ingest module. The golden
   backtest and the scorecard report the backfilled and live periods as separate rows, and
   the headline numbers come from the live period alone once it is long enough.
3. **Baselines and the scorecard (≈1 week).** Seven baselines on highs and lows by lead,
   published before any ML.
4. **The model and the scorecard page (≈2 weeks).** LightGBM quantile, conformal,
   champion–challenger, predictions stored before settlement. The React client skeleton
   (OpenAPI types, one fetch per route) and the Scorecard page are built here, and the page
   goes live with the model's first scored day. Dash keeps serving the station view.
5. **Chile on the same spine (≈1 week).** DMC stations, highs and lows. Proves the entity key.
6. **The client (≈1 week).** React station page to parity on the new tables; Dash retired.
7. **MCP server (≈1 week).** `forecast`, `observations`, `scorecard`, `explain`, `backtest`,
   all taking `as_of`; the assistant moves onto the same tools.
8. **Write-ups.** HRRR vs NBM vs ECMWF by lead; the scorecard at 60 days.
9. **Chile rain**, after 60 days of raw-model precipitation scores.
